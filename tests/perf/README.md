# 真實網站效能與體驗測試

在 YouTube 與動畫瘋的真實頁面上，比較兩個版本的擴充功能（兩個 git ref，或
ref 對工作目錄），回答兩個問題：**有沒有變慢**、**有沒有變差**（光影響應、
畫面、行為）。結尾給出 PASS／WARN／FAIL，FAIL 時結束碼為 1。

## 為什麼把測試放進版控

早期這些腳本是各自臨時寫、不進版控：每次的影片、片段、取樣方式與判斷標準
都不一樣，前後的數字沒辦法比。放進版控是為了**統一測試流程**，避免不同測試
出現不同標準。要改標準就改這裡（`lib.mjs` 的 `THRESHOLDS`、`SITES`、`PRESETS`）
並在 commit 說明原因，而不是在某次對話裡臨時換一套。測得越完整，未來的 bug
越少，改動功能時也能邊量邊修。

## 用法

需要 Chromium 與 playwright-core（`npm i -g @playwright/cli` 即可）。
`CHROMIUM_PATH` 預設為 `/Applications/Chromium.app/Contents/MacOS/Chromium`。
下面以測試跑在主螢幕（`--window 0,0`）為例；放在別的螢幕就換座標（見「螢幕」）。

```sh
# 0. 換了機器、螢幕或改了測試腳本之後：先證明標準本身可靠（都應該 PASS）
node tests/perf/selftest.mjs                     # 判定邏輯的自測，不開瀏覽器，1 秒
node tests/perf/suite.mjs --aa --window 0,0      # A/A：基準對自己，約 2 分鐘

# 1. 開發迴圈：HEAD（基準）對工作目錄（候選），YouTube 深色、預設設定
#    基準有快取時約 1 分鐘，第一次約 2 分鐘
node tests/perf/suite.mjs --window 0,0

# 2. 完整矩陣：3 個站 × 淺／深色 × 3 組設定；第 1 輪全做，第 2 輪只重跑預設設定。約 55 分鐘（登入狀態實測 53.5 分鐘）
node tests/perf/suite.mjs --mode full --window 0,0 --expect-display 2560x1440 --expect-hdr

# 3. 比兩個 commit
node tests/perf/suite.mjs --base c58326b --cand HEAD --mode full --window 0,0 --expect-hdr

# 只重算判定（不重跑）；--timings 另列每次執行各階段的秒數
node tests/perf/compare.mjs /tmp/lg-perf --timings
```

**怎麼停**：`touch /tmp/lg-perf/PAUSE`（`--out` 的目錄）會在目前這次執行結束後停下，刪掉檔案再跑一次
就從中斷處接續（做完且有效的結果會保留）；Ctrl-C／SIGTERM 會立刻停止並關掉瀏覽器。

**螢幕**：`--window x,y` 指定測試視窗的左上座標（或環境變數 `LG_PERF_WINDOW`），例如 `0,0` 是主螢幕，
`-1920,0` 是主螢幕左邊的外接螢幕。macOS 上套件啟動時會讀出該螢幕的解析度、縮放與是否 HDR，每次執行前
再讀一次，**螢幕變了（例如解析度跑掉）就停止並提示**，不會產出不可比的數字。
`--expect-display 2560x1440` 要求解析度吻合才開測；`--expect-hdr` 要求該螢幕已開啟 HDR（系統設定 ›
顯示器），且 4K 片實際收到 HDR 串流（`hdr-stream` 檢查），避免「以為測了 HDR 其實是 SDR」。
螢幕資訊寫進每個結果，新舊不一致時 `compare.mjs` 警告「數字不可比」，基準快取也隨之失效。
視窗要保持可見、別被別的視窗整個蓋住或最小化；另加了 `--disable-backgrounding-occluded-windows`
等旗標，每組設定也有 `visible` 檢查。

**不搶你的鍵盤**：Chromium 在建立第一個視窗時會取得 app 焦點（macOS 上 `open -g` 也擋不住）。
預設的 `--launch cdp` 避開了它：Chromium 以 `--no-startup-window` 啟動，測試視窗由 CDP 以背景方式建立，
再用 `connectOverCDP` 接上；設定直接在擴充功能內容腳本的 JS 環境裡寫入 `chrome.storage`，凍結畫面的比對
也在同一頁完成，全程不開額外分頁、不呼叫 `bringToFront`。**已實測**：一次完整 YouTube 執行約 2 分鐘，
每 0.2 秒記錄前景程式，全程沒有離開原本的終端機，結果的 `focusSteals` 為 0。
兩層備援：`--launch playwright`（舊方式，會搶焦點）時，每次啟動前先等鍵盤滑鼠閒置 `--idle N` 秒
（此模式預設 8）；**焦點守衛**在萬一拿到焦點時，0.25 秒內還給原本的程式，次數記在 `focusSteals`。
守衛會把前景還給「Chromium 之前的那個程式」，所以測試期間不要自己點進測試視窗。

其他：
- 基準以「擴充功能的 commit sha ＋ 測試腳本版本（`lib.mjs`、`run.mjs` 內容的雜湊）」快取，兩者都沒變
  才沿用；候選每次都重跑。改了窗口、等待或取樣方式，舊基準自動作廢；`compare.mjs` 看到兩邊腳本版本
  不同會直接 FAIL，不會拿不同量法的數字互比。
- `quick` 用 YouTube **深色**：YouTube 的文字遮罩（scrim）只在深色時啟動，淺色時永遠是 0，只跑淺色的
  開發迴圈等於沒測到文字可讀性。
- `--clips ani-white` 之類可只跑指定片段，做針對性的開發迴圈。
- 每個站／主題內基準與候選**交錯**執行，網路與時段的漂移會同時落在兩邊。
- 量測中途插播廣告（長影片的中段廣告）時，只重做被打斷的那一段，不整次重跑；連續 3 次都被打斷才判失敗。
- 有效性檢查失敗（廣告沒跳過、沒升到指定畫質、主題或設定沒套用、影片沒在播、頁面不可見、
  凍結畫面不穩定）會整次重試一次；數字只在有效的執行上比較。
- 每次執行結束會等 Chromium 確實關閉（不留孤兒程序吃 CPU），並刪掉約 70 MB 的設定檔目錄；
  要保留除錯用 `--keep-profile`。
- **本機掛鉤**：不進版控的本機自訂（例如某次執行要帶的瀏覽器狀態）放在 `LG_PERF_HOOKS` 指向的模組，
  或 `tests/perf/local/hooks.mjs`（請用 `.git/info/exclude` 排除，只存在本機）。它可匯出 `session`（標籤）
  與 `beforeNavigate({ ctx, site, url })`。不同 `session` 的結果不會互比、也不會沿用為基準；
  有掛鉤時不寫入固定訪客的 cookie。沒有掛鉤時一律是 `anonymous`。
- 只能用 Chromium：品牌版 Chrome 會忽略 `--load-extension`。
- `--sites yt,yt4k,ani`、`--themes light,dark`、`--presets …`、`--rounds N` 可個別覆寫。
- **不可封鎖或腳本移除廣告。** 未登入時兩站都有廣告：腳本一律等廣告播完、跳過鈕出現後再點跳過；
  動畫瘋另有分級確認框，直接點「同意」。

## 為什麼這樣排：時間花在哪

一次 YouTube 執行（3 組設定）實測約 278 秒，其中約 79% 是「每組設定 × 每個片段」的播放
（CPU 一輪、響應一輪、凍結畫面），啟動與廣告約 9%，版面與換片檢查約 12%。所以加速集中在這幾點
（`--timings` 可看每次執行各階段的實際秒數，下一輪優化先看它）：

| 做法 | 省下 |
|---|---|
| 量測窗口 24 秒 → 12 秒（足夠穩態 CPU，也涵蓋有趣的核心）；開窗前的暖機 3.5 → 2.5 秒 | 每組設定每個片段約 73 → 42 秒 |
| `full` 第 2 輪只重跑預設設定：極端設定的顯示一輪就看得出，第 2 輪是為了雜訊校準與 CPU 變異 | 第 2 輪約少 65% |
| 版面抖動與換片檢查只在 YouTube 淺色做一次；`quick` 預設不做 | 每次執行少 35–50 秒 |
| 基準以 sha 快取，只重跑候選 | 開發迴圈約減半 |
| 設定生效、重新排版等固定等待縮短到實際需要的長度 | 每次執行少約 8 秒 |
| 無擴充功能對照組只跑預設設定、一個片段 | 每組僅約 40 秒 |

`full` 從約 5.6 小時（2 輪全做）降到實測 53.5 分鐘（登入狀態；對照組量一次就保存，之後更短）；`quick` 實測每次執行 51 秒（載入 9、量測 41），整個迴圈約 1–2 分鐘。
新舊與對照組**不能並行**：同時跑會互搶 CPU／GPU，資源數字就失真。

## 檔案

| 檔案 | 作用 |
|---|---|
| `lib.mjs` | 片段、設定預設、判定門檻、參數解析、螢幕偵測、建置擴充功能；所有工具共用同一份標準 |
| `run.mjs` | 一次執行：一個站 × 一個主題 × 一個版本，載入一次頁面，輪流套用各組設定 |
| `suite.mjs` | 排程整個矩陣、快取基準、失敗重試、螢幕守門、暫停，最後呼叫 `compare.mjs` |
| `compare.mjs` | 表格、門檻判定、凍結畫面像素比對、結論與結束碼 |
| `selftest.mjs` | 用手造的結果檢驗判定邏輯：相同要 PASS，每種退步要被對應的門檻抓到 |

## 測什麼

**每個站、主題、設定組、片段**：
1. **CPU**：片段播放期間 Chromium `Performance.getMetrics` 的增量
   （`TaskDuration`、`ScriptDuration`、`RecalcStyleDuration`、`LayoutCount`），
   加長任務與影片掉幀。這一輪頁面內沒有任何測試程式碼，數字才乾淨。
2. **CPU／GPU／RAM 實際用量**：從頁面外面每秒讀一次整個 Chromium 程序群
   （依 `--user-data-dir` 找出，分成瀏覽器、渲染、GPU、其他），算出各類程序在片段期間
   用掉的 CPU（以單一核心的百分比計）、RAM 平均與尖峰、視窗內的 RAM 成長（洩漏線索）；
   GPU 另讀 macOS 驅動回報的整機 GPU 忙碌 %（`ioreg`，含別的視窗，雜訊較大，
   所以只當輔助、門檻較寬）。CDP 的主執行緒指標看不到 GPU 程序與記憶體，這一層補上。
3. **響應**：另一輪以 10 Hz 讀擴充功能自己的 `#lg-ambient-canvas`、`#lg-scrim`、
   `#lg-glow`，與影片亮度做相關，得到延遲（`lag`，解析度 100 ms）與振幅
   （`amb swing`）。
4. **凍結畫面**：在固定的媒體時間暫停，連拍兩張（間隔 1 秒，前面先等 1.5 秒讓光暈收斂）肉眼無法分辨的差異內才算
   穩定（否則重試，最後標為不穩定並排除，不拿來比），截取播放器與周邊（不含每次都
   換的推薦欄），用像素差比對兩個版本。這取代了「隨機時間截圖＋肉眼」，同一時間點
   同一張畫面才有資格比。

**無擴充功能的對照組**（`--off`，完整模式預設開）：同一頁、同一片段、同樣的螢幕與色彩設定，
不載入擴充功能，只量資源。「擴充功能自己的成本」＝這一版減對照組，比單看總量準，
也能回答「4K HDR 這種本來就很吃資源的影片，插件多出多少」。比較時看基準與候選各自的
額外成本，候選的額外 CPU 比基準多出 5 點（單核百分比）以上就警告。

**YouTube 淺色、預設設定另測（只在 `full` 模式）**：劇院模式 ×8、捲動 ×10、視窗縮放 ×6 的版面抖動；
站內換片（SPA 導覽）後環境光層是否重綁到新影片、沒有重複也沒有消失。

**不需基準的檢查**（`checks`，任一失敗＝FAIL）：廣告已通過、擴充功能已啟動
（3 個 canvas）、主題已套用、4K 片確實升到 2160p、設定預設確實生效、片段確實在播、
環境光與影片相關（影片本身有足夠起伏時）、頁面可見（不要求焦點）、凍結畫面穩定、量測沒被廣告連續打斷、
refract 貼圖都已寫入、換片後狀態正常、頁面沒有錯誤。

## 設定預設與主題：為什麼是這幾組

擴充功能的目標是「讓介面跟著影片的光影走，且任何畫面下字都讀得到」。
預設值只代表一般使用者，真正會壞的在極端設定，所以每個站都在淺色與深色各跑：

| 預設 | 透明度 | 環境光 | 文字對比 | 用途 |
|---|---|---|---|---|
| `default` | 50 | 70 | 4.5 | 設計預設，日常基準 |
| `max-glass` | 100 | 100 | 1.5 | 玻璃最透、光最強、可讀性補償最少：全白或高亮畫面下字會不會讀不到 |
| `solid-glow` | 0 | 100 | 1.5 | 玻璃最實、光最強、可讀性補償最少：強光溢出與實色底板的搭配、光暈有沒有蓋到內容 |

淺／深色都要測，因為 scrim 的底色、光暈的混色與可讀性求解在兩種主題下是不同路徑
（`contrast.js` 依 `html[dark]` 分流）。YouTube 的主題跟隨系統色彩（以 Chromium 的
`colorScheme` 設定），動畫瘋改寫 `html[data-theme]`。

## 測試影片，與為什麼選它們

挑片的原則：同時打到**光影劇烈變動**、**全白畫面**與**極限解碼負載**三種壓力，
不是隨便一支影片。

| 站 | 片段 | 為什麼 | 主要量什麼 |
|---|---|---|---|
| YouTube `55moNn0leAU` | 量 1:41–1:53 | 燈光／光影變化劇烈，環境光與光暈每幀都在大幅改變 | 響應延遲、每幀成本 |
| YouTube `xb-Oh2z1H88` | 量 0:34–0:46 | 4K 60 fps 高負載影片（標題為 8K HDR Dolby Vision 示範片），量擴充功能在影片本身已很吃資源時多出的額外支出，以及極限環境下響應與效果是否還符合預期 | 額外 CPU、掉幀、極限下的響應 |
| 動畫瘋 `sn=12866` | 核心 17:18–17:27，量 17:16–17:28 | 畫面由全黑切入全白：最壞的亮度跳變，檢查全白底下的玻璃透明度與文字（選單、標題）是否仍可讀 | 文字可讀性（凍結畫面）、scrim |
| 動畫瘋 `sn=12866` | 核心 20:00–20:10，量 19:59–20:11 | 激烈戰鬥，光影快速連續變動 | 劇烈變動下的響應與耗能 |

每個量測窗口 12 秒，開窗前先播 2.5 秒暖機，讓擴充功能在重點開始前就已進入追蹤。
`SITES` 裡每段另有凍結畫面的媒體時間點（`stills`）。

**4K 片與 HDR**：視窗所在的螢幕必須支援並開啟 HDR，且瀏覽器不能被強制成 sRGB 色彩設定（預設的
`--launch cdp` 不會；舊的 `--launch playwright` 要靠 `--expect-hdr` 拿掉該旗標），YouTube 才會送 HDR 串流。
實測：HDR 開啟的主螢幕上收到 2160p60、AV1 10-bit、`smpte2084 (PQ) / bt2020`；不支援 HDR 的螢幕上只收到
2160p60、VP9、`bt709`（SDR），那時 HDR 解碼路徑**沒有**被測到。結果裡的 `display …HDR` 標記與串流的
`color` 欄位會註明這次是哪一種；`quality-reached` 確保真的升到 2160p，`--expect-hdr` 下的 `hdr-stream`
確保真的是 HDR。

### 影片下架或換掉時

重點是「符合標準」而不是「同一支影片」。換片後把新的 ID／時間點、符合哪一條，
更新到上表與 `lib.mjs` 的 `SITES`，並用新片重跑新舊版本重建基準：

1. **光影劇烈、連續變動**：數秒內亮度與主色大幅且反覆變化（演唱會燈光、爆炸或
   戰鬥場面、閃光）。
2. **黑到全白的突變**：同一支片裡有純黑淡入或硬切到接近純白的鏡頭，持續數秒。
3. **極限解碼負載**：可選到 2160p60，位元率高、畫面複雜；`quality-reached` 要能過。
4. **能穩定播放**：不需登入、沒有年齡以外的限制（動畫瘋分級框可接受）。
5. **來源穩定、長度足夠**：優先官方頻道或長期不會下架的作品；符合條件的連續片段至少 15 秒（量 12 秒加暖機）。

## 怎麼讀結果

- **FAIL（硬門檻）**：候選的有效性檢查失敗、掉幀比基準多、環境光延遲多於基準
  100 ms 以上、環境光振幅掉到基準的 85% 以下、元素數量與基準不同、凍結畫面像素
  超出容許；以及兩邊不可比：測試腳本版本不同、影片在頁面上的位置尺寸不同（版面不一致）。
- **WARN（軟門檻）**：主執行緒時間、長任務超出基準自己的輪間雜訊（至少 ×1.10）；
  全部程序 CPU 多出 8 點以上、GPU 程序 CPU 多出 5 點以上、整機 GPU 忙碌多出 10 點以上、
  RAM 高出 15% 以上、視窗內 RAM 多成長 80 MB 以上；擴充功能自己的額外 CPU 比基準多 5 點以上。
  這些都是「異常提示」，要搭配多輪與對照組判讀，單輪的 GPU 數字尤其會被其他視窗影響。
- 凍結畫面的容許值會用「基準對基準」的兩輪差距自我校準（取 1.5 倍與固定下限的較大者），
  所以跑兩輪以上才有校準；只跑一輪時用固定下限。
- 頁面層級的 CPU 差異常小於雜訊，微觀優化（例如快取 `matchMedia`）在這裡不一定看得出；
  不要因此否定它，也不要拿單輪數字下結論。第一輪用全新 profile 偏冷。
- 畫質固定：YouTube 兩支片分別固定在 1080p 與 2160p（自動畫質每次載入都可能不同，
  480p 與 1080p 的 CPU 和畫面根本不能比）；基準與候選實際播放的解析度與編碼不同時
  會警告。動畫瘋無法在腳本中指定畫質，只做同樣的警告。
- 懷疑門檻誤報時，先跑 `--aa`（基準對自己，程式碼完全相同）：應該 PASS；不是的話是
  環境雜訊（螢幕、網路、畫質）而不是程式，要先排除才能相信後面的數字。
- 判定邏輯本身改動後跑 `selftest.mjs`。像素比對需要瀏覽器，不在自測內，由 A/A 驗證。
