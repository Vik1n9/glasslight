# 真實網站效能與體驗測試

在 YouTube 與動畫瘋的真實頁面上，比較兩個版本的擴充功能（兩個 git ref，
或 ref 對工作目錄）在「CPU 消耗」與「光影響應」上的差異。

## 為什麼把測試腳本放進版控

這些腳本一開始只是各自臨時寫、不進版控。問題是每次測試用的影片、
片段、取樣方式、判斷標準都不一樣，前後兩次的數字沒辦法比較，「這次改動
有沒有變慢／有沒有變差」也就沒有共同答案。放進版控是為了**統一測試流程**：
同一組片段、同一套指標、同一種取樣，避免不同測試出現不同標準。
要改標準就改這裡並寫在 commit 裡，而不是在某次對話裡臨時換一套。

## 用法

```sh
# 需要 Chromium 與 playwright-core（npm i -g @playwright/cli 即可）
# CHROMIUM_PATH 預設 /Applications/Chromium.app/Contents/MacOS/Chromium
OUT=/tmp/lg-perf
for r in 1 2; do for v in "c58326b old" "HEAD new"; do set -- $v
  node tests/perf/run.mjs --site yt  --ref $1 --label $2 --round $r --out $OUT
  node tests/perf/run.mjs --site ani --ref $1 --label $2 --round $r --out $OUT
done; done
node tests/perf/compare.mjs $OUT
```

- 新舊版本**交錯**執行（old、new、old、new），不要先跑完一個版本再跑另一個，
  才不會把網路與時段的變動算成版本差異。
- 每輪使用全新 profile，第一輪偏冷、數字偏高；有疑慮時以第 2 輪起為準。
- `--ref WORKTREE`（預設）測目前工作目錄；建置時一律移除 `dev-reload`，
  免得擴充功能在測試中途重載自己。
- 只能用 Chromium：品牌版 Chrome 會忽略 `--load-extension`。
- **不可封鎖或腳本移除廣告。** 未登入時兩站都有廣告：腳本一律等廣告播完、
  跳過鈕出現後再點跳過；動畫瘋另有分級確認框，直接點「同意」。

## 兩個測試站、三段片段，為什麼選它們

擴充功能的工作是「讓介面跟著影片的光影走，並且在任何畫面上字都讀得到」。
所以挑片段要能同時打到兩種壓力：**光影劇烈變動**（量響應與耗能），以及
**全白畫面**（量透明度與文字可讀性）。不是隨便一支影片。

| 片段 | 位置 | 為什麼選它 | 主要量什麼 |
|---|---|---|---|
| YouTube `55moNn0leAU` | 從 1:41（`t=101`）起約 20 秒 | 燈光／光影變化劇烈，環境光與光暈每幀都在大幅改變 | 響應延遲、每幀成本、掉幀 |
| 動畫瘋 `sn=12866` | 17:18–17:27 | 畫面由全黑切入全白：最壞情況的亮度跳變，檢查全白底下的玻璃透明度與文字（選單、標題）是否仍可讀 | 文字可讀性（截圖）、scrim 強度 |
| 動畫瘋 `sn=12866` | 20:00–20:10 | 激烈戰鬥，畫面光影快速且連續變動 | 劇烈變動下的響應與耗能 |

`run.mjs` 實際取樣的視窗比核心區間前面多 4 秒、後面多 3 秒，
讓擴充功能在重點開始前就已進入追蹤狀態。

### 影片下架或換掉時

重點是「符合標準」而不是「同一支影片」。換片時找符合下列條件的，
並把新的 ID／時間點、以及它符合哪一條，更新到上面的表格與 `run.mjs` 的 `SITES`：

1. **光影劇烈、連續變動**：數秒內亮度與主色大幅且反覆變化（演唱會燈光、
   爆炸或戰鬥場面、閃光），用來測響應與耗能。
2. **黑到全白的突變**：同一支片裡有純黑淡入或硬切到接近純白的鏡頭，
   持續至少數秒，用來測全白底下的透明度與文字顯示。
3. **能穩定播放**：不需登入、沒有區域或年齡以外的限制，高畫質、約 30 fps 以上；
   動畫瘋的分級確認框可以接受，其他阻擋不行。
4. **來源穩定**：優先官方頻道或長期不會下架的作品；片段長度足夠（≥ 20 秒）。

換片後舊數字不再與新數字相比：同一個基準線要用新片重跑新舊版本。

## 指標

- **CPU**：Chromium `Performance.getMetrics` 的 `TaskDuration`、`ScriptDuration`、
  `RecalcStyleDuration`／`Count`、`LayoutCount` 在片段播放期間的增量，加上長任務
  次數與毫秒、影片掉幀數。
- **響應**：以 10 Hz 讀取擴充功能自己的 `#lg-ambient-canvas`、`#lg-scrim`、
  `#lg-glow`，與影片本身的亮度做相關，找出最相符的位移＝延遲（`lagMs`），
  並記錄振幅（`ambStd`）與最大單步變化（`ambMaxStep`）。延遲變大或振幅變小
  代表跟不上；scrim 範圍用來看全白下的文字底板有沒有生效。
- **體驗**：全白片段每約 2.5 秒截一張圖（`shot-*.png`），**需要肉眼看**，
  確認選單與標題文字在全白下仍可讀；另有 `lg-clear`／refract filter／canvas
  數量與 root class 的狀態比對（YouTube）。
- **版面抖動**（YouTube）：劇院模式 ×8、捲動 ×10、視窗縮放 ×6。

## 判讀注意

- 頁面層級的 CPU 差異常小於雜訊，微觀的優化（例如快取 `matchMedia`）在這裡
  不一定看得出來；不要因此否定它，也不要拿單輪數字下結論。
- 「體驗有沒有變差」以響應指標加上肉眼看截圖為準，兩者都要。
