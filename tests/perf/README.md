# 真實網站效能與體驗測試

在 YouTube 與動畫瘋的真實頁面上，比較兩個版本的擴充功能（兩個 git ref，或
ref 對工作目錄），回答兩個問題：**有沒有變慢**、**有沒有變差**（光影響應、
畫面、行為）。結尾給出 PASS／WARN／FAIL，FAIL 時結束碼為 1。

## 為什麼把測試放進版控

早期這些腳本是各自臨時寫、不進版控：每次的影片、片段、取樣方式與判斷標準
都不一樣，前後的數字沒辦法比。放進版控是為了**統一測試流程**，避免不同測試
出現不同標準。要改標準就改這裡（`lib.mjs` 的 `THRESHOLDS`、`SITES`、`PRESETS`）
並在 commit 說明原因，而不是在某次對話裡臨時換一套。測得越完整，未來的 bug
越少，改動功能時也能邊量邊修。

## 用法

需要 Chromium 與 playwright-core（`npm i -g @playwright/cli` 即可）。
`CHROMIUM_PATH` 預設為 `/Applications/Chromium.app/Contents/MacOS/Chromium`。

```sh
# 0. 換了機器、螢幕或改了標準之後：先證明標準本身可靠（都應該 PASS）
node tests/perf/selftest.mjs                      # 判定邏輯的自測，不開瀏覽器，1 秒
node tests/perf/suite.mjs --aa --window -1920,0   # A/A：基準對自己，約 3 分鐘

# 1. 開發迴圈：HEAD（基準）對工作目錄（候選），約 6 分鐘
node tests/perf/suite.mjs --window -1920,0

# 2. 完整矩陣：3 個站 × 淺／深色 × 3 組設定 × 2 輪，約 2 小時
node tests/perf/suite.mjs --mode full --window -1920,0

# 3. 比兩個 commit
node tests/perf/suite.mjs --base c58326b --cand HEAD --mode full --window -1920,0

# 只重算判定（不重跑）
node tests/perf/compare.mjs /tmp/lg-perf
```

**怎麼停**：`touch /tmp/lg-perf/PAUSE`（`--out` 的目錄）會在目前這次執行結束後停下，
刪掉檔案再跑一次就從中斷處接續（做完且有效的結果會保留）；Ctrl-C／SIGTERM 會立刻
停止並關掉瀏覽器。

**螢幕守門**：`--window x,y` 指定測試視窗的左上座標，例如 `-1920,0` 開在主螢幕左邊的
外接螢幕，不干擾你正在用的開發頁面（或用環境變數 `LG_PERF_WINDOW`）。macOS 上
套件啟動時會讀出該座標所在螢幕的解析度、縮放與是否 HDR，每次執行前再讀一次，
**螢幕變了（例如解析度跑掉）就停止並提示**，不會產出不可比的數字。
`--expect-display 2560x1440` 可要求解析度必須吻合才開測；`--expect-hdr` 要求該螢幕必須已開啟 HDR
（macOS 系統設定 › 顯示器），且 4K 片實際收到的是 HDR 串流（`hdr-stream` 檢查），
否則中止或判無效，避免「以為測了 HDR 其實是 SDR」。Playwright 預設強制 sRGB 色彩設定，會讓頁面看不到
螢幕的 HDR（YouTube 只送 SDR），所以 `--expect-hdr` 也會拿掉該旗標，且對該次套件的每個站一律如此，
維持同一條色彩管線。螢幕資訊寫進每個結果，
新舊不一致時 `compare.mjs` 警告「數字不可比」，基準快取也隨之失效。
**不搶你的鍵盤**：測試視窗放在另一個螢幕、全程不需要焦點，腳本不呼叫 `bringToFront`、不開
額外分頁（設定直接在擴充功能內容腳本的 JS 環境裡寫入 `chrome.storage`，凍結畫面的比對也在
同一頁完成）。Chromium 啟動時會搶一次 app 焦點，所以 `run.mjs` 內建「焦點守衛」：記住原本在
前景的程式，Chromium 一拿到焦點就在 1 秒內還回去，次數寫進結果的 `focusSteals`（macOS）。
視窗要保持可見、別被別的視窗蓋住或最小化（被遮住會降低渲染頻率；我們另加了
`--disable-backgrounding-occluded-windows` 等旗標，且每組設定都有 `visible` 檢查）。
守衛會把前景還給「Chromium 之前的那個程式」，所以測試期間不要自己點進測試視窗。

Chromium 一啟動就會取得 app 焦點（macOS 上 `open -g` 也擋不住），這是唯一會打斷你輸入的時刻。
預設的 `--launch cdp` 把它避開了：Chromium 以 `--no-startup-window` 啟動（沒有視窗，也就沒有東西可搶焦點），
測試視窗改由 CDP 以背景方式建立，再用 `connectOverCDP` 接上。**已實測**：一次完整 YouTube 執行約
2 分鐘，每 0.2 秒記錄前景程式，全程沒有離開原本的終端機，結果的 `focusSteals` 為 0。

另有兩層備援：
- `--launch playwright`（舊方式，由 Playwright 啟動，會搶焦點）時，每次啟動前先等你的鍵盤滑鼠
  閒置 `--idle N` 秒（此模式預設 8，0 關閉），你停手才開。
- **焦點守衛**：萬一仍拿到焦點，0.25 秒內還給原本的程式；次數記在 `focusSteals`。

其他：
- 基準以 commit sha 快取，基準沒變就不重跑；候選每次都重跑。
- 每個站／主題內基準與候選**交錯**執行，網路與時段的漂移會同時落在兩邊。
- 有效性檢查失敗（廣告沒跳過、沒升到指定畫質、主題或設定沒套用、影片沒在播、
  頁面不在前景、凍結畫面不穩定）會自動重試一次；數字只在有效的執行上比較。
- 只能用 Chromium：品牌版 Chrome 會忽略 `--load-extension`。
- `--sites yt,yt4k,ani`、`--themes light,dark`、`--presets …`、`--rounds N` 可個別覆寫。
- **不可封鎖或腳本移除廣告。** 未登入時兩站都有廣告：腳本一律等廣告播完、
  跳過鈕出現後再點跳過；動畫瘋另有分級確認框，直接點「同意」。

## 為什麼這樣排：時間花在哪

一次 YouTube 執行（3 組設定）實測約 278 秒，其中約 79% 是「每組設定 × 每個片段」的播放
（CPU 一輪、響應一輪、凍結畫面），啟動與廣告約 9%，版面與換片檢查約 12%。所以加速集中在這幾點
（`--timings` 可看每次執行各階段的實際秒數，下一輪優化先看它）：

| 做法 | 省下 |
|---|---|
| 量測窗口 24 秒 → 12 秒（足夠穩態 CPU，也涵蓋有趣的核心）；開窗前的暖機 3.5 → 2.5 秒 | 每組設定每個片段約 73 → 42 秒 |
| `full` 第 2 輪只重跑預設設定：極端設定的顯示一輪就看得出，第 2 輪是為了雜訊校準與 CPU 變異 | 第 2 輪約少 65% |
| 版面抖動與換片檢查只在 YouTube 淺色做一次；`quick` 預設不做 | 每次執行少 35–50 秒 |
| 基準以 sha 快取，只重跑候選 | 開發迴圈約減半 |
| 設定生效、重新排版等固定等待縮短到實際需要的長度 | 每次執行少約 8 秒 |
| 無擴充功能對照組只跑預設設定、一個片段 | 每組僅約 40 秒 |

粗估 `full` 從約 5.6 小時（2 輪全做）降到約 75 分鐘，`quick` 約 1.5–3 分鐘。
新舊與對照組**不能並行**：同時跑會互搶 CPU／GPU，資源數字就失真。

## 檔案

| 檔案 | 作用 |
|---|---|
| `lib.mjs` | 片段、設定預設、判定門檻、參數解析、螢幕偵測、建置擴充功能；所有工具共用同一份標準 |
| `run.mjs` | 一次執行：一個站 × 一個主題 × 一個版本，載入一次頁面，輪流套用各組設定 |
| `suite.mjs` | 排程整個矩陣、快取基準、失敗重試、螢幕守門、暫停，最後呼叫 `compare.mjs` |
| `compare.mjs` | 表格、門檻判定、凍結畫面像素比對、結論與結束碼 |
| `selftest.mjs` | 用手造的結果檢驗判定邏輯：相同要 PASS，每種退步要被對應的門檻抓到 |

## 測什麼

**每個站、主題、設定組、片段**：
1. **CPU**：片段播放期間 Chromium `Performance.getMetrics` 的增量
   （`TaskDuration`、`ScriptDuration`、`RecalcStyleDuration`、`LayoutCount`），
   加長任務與影片掉幀。這一輪頁面內沒有任何測試程式碼，數字才乾淨。
2. **CPU／GPU／RAM 實際用量**：從頁面外面每秒讀一次整個 Chromium 程序群
   （依 `--user-data-dir` 找出，分成瀏覽器、渲染、GPU、其他），算出各類程序在片段期間
   用掉的 CPU（以單一核心的百分比計）、RAM 平均與尖峰、視窗內的 RAM 成長（洩漏線索）；
   GPU 另讀 macOS 驅動回報的整機 GPU 忙碌 %（`ioreg`，含別的視窗，雜訊較大，
   所以只當輔助、門檻較寬）。CDP 的主執行緒指標看不到 GPU 程序與記憶體，這一層補上。
3. **響應**：另一輪以 10 Hz 讀擴充功能自己的 `#lg-ambient-canvas`、`#lg-scrim`、
   `#lg-glow`，與影片亮度做相關，得到延遲（`lag`，解析度 100 ms）與振幅
   （`amb swing`）。
4. **凍結畫面**：在固定的媒體時間暫停，連拍兩張（間隔 700 ms）肉眼無法分辨的差異內才算
   穩定（否則重試，最後標為不穩定並排除，不拿來比），截取播放器與周邊（不含每次都
   換的推薦欄），用像素差比對兩個版本。這取代了「隨機時間截圖＋肉眼」，同一時間點
   同一張畫面才有資格比。

**無擴充功能的對照組**（`--off`，完整模式預設開）：同一頁、同一片段、同樣的螢幕與色彩設定，
不載入擴充功能，只量資源。「擴充功能自己的成本」＝這一版減對照組，比單看總量準，
也能回答「4K HDR 這種本來就很吃資源的影片，插件多出多少」。比較時看基準與候選各自的
額外成本，候選的額外 CPU 比基準多出 5 點（單核百分比）以上就警告。

**YouTube 預設設定另測**：劇院模式 ×8、捲動 ×10、視窗縮放 ×6 的版面抖動；
站內換片（SPA 導覽）後環境光層是否重綁到新影片、沒有重複也沒有消失。

**不需基準的檢查**（`checks`，任一失敗＝FAIL）：廣告已通過、擴充功能已啟動
（3 個 canvas）、主題已套用、4K 片確實升到 2160p、設定預設確實生效、片段確實在播、
環境光與影片相關（影片本身有足夠起伏時）、頁面在前景、凍結畫面穩定、refract 貼圖都已寫入、
換片後狀態正常、頁面沒有錯誤。

## 設定預設與主題：為什麼是這幾組

擴充功能的目標是「讓介面跟著影片的光影走，且任何畫面下字都讀得到」。
預設值只代表一般使用者，真正會壞的在極端設定，所以每個站都在淺色與深色各跑：

| 預設 | 透明度 | 環境光 | 文字對比 | 用途 |
|---|---|---|---|---|
| `default` | 50 | 70 | 4.5 | 設計預設，日常基準 |
| `max-glass` | 100 | 100 | 1.5 | 玻璃最透、光最強、可讀性補償最少：全白或高亮畫面下字會不會讀不到 |
| `solid-glow` | 0 | 100 | 1.5 | 玻璃最實、光最強、可讀性補償最少：強光溢出與實色底板的搭配、光暈有沒有蓋到內容 |

淺／深色都要測，因為 scrim 的底色、光暈的混色與可讀性求解在兩種主題下是不同路徑
（`contrast.js` 依 `html[dark]` 分流）。YouTube 的主題跟隨系統色彩（以 Chromium 的
`colorScheme` 設定），動畫瘋改寫 `html[data-theme]`。

## 測試影片，與為什麼選它們

挑片的原則：同時打到**光影劇烈變動**、**全白畫面**與**極限解碼負載**三種壓力，
不是隨便一支影片。

| 站 | 片段 | 為什麼 | 主要量什麼 |
|---|---|---|---|
| YouTube `55moNn0leAU` | 1:41 起約 20 秒 | 燈光／光影變化劇烈，環境光與光暈每幀都在大幅改變 | 響應延遲、每幀成本 |
| YouTube `xb-Oh2z1H88` | 0:34–0:58 | 4K 60 fps 高負載影片（標題為 8K HDR Dolby Vision 示範片），量擴充功能在影片本身已很吃資源時多出的額外支出，以及極限環境下響應與效果是否還符合預期 | 額外 CPU、掉幀、極限下的響應 |
| 動畫瘋 `sn=12866` | 17:18–17:27 | 畫面由全黑切入全白：最壞的亮度跳變，檢查全白底下的玻璃透明度與文字（選單、標題）是否仍可讀 | 文字可讀性（凍結畫面）、scrim |
| 動畫瘋 `sn=12866` | 20:00–20:10 | 激烈戰鬥，光影快速連續變動 | 劇烈變動下的響應與耗能 |

每個量測窗口 12 秒，開窗前先播 2.5 秒暖機，讓擴充功能在重點開始前就已進入追蹤。
`SITES` 裡每段另有凍結畫面的媒體時間點（`stills`）。

**4K 片的已知限制**：視窗所在的螢幕必須支援並開啟 HDR，YouTube 才會送 HDR 串流。
在不支援 HDR 的螢幕上實際收到的是 2160p60、VP9 profile 0、`bt709`（SDR），
HDR 解碼路徑**沒有**被測到，只測到 4K60 的解碼與傳輸負載。結果裡的
`display …HDR` 標記與串流的 `color` 欄位會註明這次到底是哪一種。
`quality-reached` 檢查確保至少真的升到 2160p。

### 影片下架或換掉時

重點是「符合標準」而不是「同一支影片」。換片後把新的 ID／時間點、符合哪一條，
更新到上表與 `lib.mjs` 的 `SITES`，並用新片重跑新舊版本重建基準：

1. **光影劇烈、連續變動**：數秒內亮度與主色大幅且反覆變化（演唱會燈光、爆炸或
   戰鬥場面、閃光）。
2. **黑到全白的突變**：同一支片裡有純黑淡入或硬切到接近純白的鏡頭，持續數秒。
3. **極限解碼負載**：可選到 2160p60，位元率高、畫面複雜；`quality-reached` 要能過。
4. **能穩定播放**：不需登入、沒有年齡以外的限制（動畫瘋分級框可接受）。
5. **來源穩定、長度足夠**：優先官方頻道或長期不會下架的作品，片段 ≥ 20 秒。

## 怎麼讀結果

- **FAIL（硬門檻）**：候選的有效性檢查失敗、掉幀比基準多、環境光延遲多於基準
  100 ms 以上、環境光振幅掉到基準的 85% 以下、元素數量與基準不同、凍結畫面像素
  超出容許。
- **WARN（軟門檻）**：主執行緒時間、長任務超出基準自己的輪間雜訊（至少 ×1.10）；
  全部程序 CPU 多出 8 點以上、GPU 程序 CPU 多出 5 點以上、整機 GPU 忙碌多出 10 點以上、
  RAM 高出 15% 以上、視窗內 RAM 多成長 80 MB 以上；擴充功能自己的額外 CPU 比基準多 5 點以上。
  這些都是「異常提示」，要搭配多輪與對照組判讀，單輪的 GPU 數字尤其會被其他視窗影響。
- 凍結畫面的容許值會用「基準對基準」的兩輪差距自我校準（取 1.5 倍與固定下限的較大者），
  所以跑兩輪以上才有校準；只跑一輪時用固定下限。
- 頁面層級的 CPU 差異常小於雜訊，微觀優化（例如快取 `matchMedia`）在這裡不一定看得出；
  不要因此否定它，也不要拿單輪數字下結論。第一輪用全新 profile 偏冷。
- 畫質固定：YouTube 兩支片分別固定在 1080p 與 2160p（自動畫質每次載入都可能不同，
  480p 與 1080p 的 CPU 和畫面根本不能比）；基準與候選實際播放的解析度與編碼不同時
  會警告。動畫瘋無法在腳本中指定畫質，只做同樣的警告。
- 懷疑門檻誤報時，先跑 `--aa`（基準對自己，程式碼完全相同）：應該 PASS；不是的話是
  環境雜訊（螢幕、網路、畫質）而不是程式，要先排除才能相信後面的數字。
- 判定邏輯本身改動後跑 `selftest.mjs`。像素比對需要瀏覽器，不在自測內，由 A/A 驗證。
